### 10.3 Why every workflow is manual — and the fixed order

Each of the five starts only two ways: `workflow_dispatch` (a human clicks **Run workflow**) or a `push:` list of branches.

| Workflow | Trigger | Automatic on `main`? |
|---|---|---|
| Windows Engineering Build | `push` → `phase2-correct`, `feature/p2-protocol-completion` | **No — `main` is not listed** |
| WS-I Release Windows Installer | `workflow_dispatch` only | **No** |
| Deploy mobile API preview | `workflow_dispatch` only | **No** |
| Deploy cyvoriq-www Pages | `workflow_dispatch` only | **No** |
| Deploy cyvoriq-admin Pages | `workflow_dispatch` only | **No** |

Nothing runs on `main` without a hand on the button — by design. WS-I's own header: *"Trigger is `workflow_dispatch` ONLY. No push, no schedule, no tag."* That is why the three commits today started nothing, and why the Actions page correctly shows 08-Oct as its latest run.

**WS-I builds nothing itself.** The order is fixed by dependency:

1. **Windows Engineering Build** → tests, packages, runs the selftest and the payload floor, uploads the artifact.
2. **WS-I, `publish=false`** → downloads that artifact, computes SHA-256, writes a candidate manifest *into the workspace only*, prints it and `git diff`. **Commits nothing, uploads nothing — the inspection stop.**
3. **WS-I, `publish=true` + a version string** → creates a new tag `v{version}-eng-{sha7}`, uploads the ZIP and `SHA256SUMS.txt` as a pre-release, commits the manifest to `main`.
4. **Deploy mobile API preview** → rebuilds the Worker. **Mandatory after step 3.**
5. **Deploy cyvoriq-www / cyvoriq-admin** → only when the dashboard interface itself changed.

### 10.4 Why step 4 is mandatory — the read path, proven in code

Every field on the dashboard card comes from one place:

> `apps/web/src/site/CustomerWorkspaceShell.tsx:203` — *"every field below is read from `build-manifest.json` through `GET /v1/me/entitlement`"*

and the manifest reaches the API through a **build-time import**:

> `services/api/src/entitlement.ts:88` — `import committedBuild from "../../../apps/web/public/build-manifest.json"`

Because it is compiled *into* the Worker, the running Worker keeps serving the manifest it was built with **until it is rebuilt**. This is the two-deploy trap the pipeline calls **P6**. Publishing alone leaves the dashboard showing the old number.
