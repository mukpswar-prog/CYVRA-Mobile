### THE LESSON FROM `HAP-001` — read this before writing any more parser

The first fix **passed its unit test and failed on the phone.** `service list`
prefixes every entry with its binder index:

```
222	vibrator: [android.os.IVibratorService]
```

The parser matched only a name at the *start* of the line, so it could never
match — while my synthetic fixture, which omitted the index, passed cleanly.
The suite was green and the device was wrong.

**Consequence, and it is now house rule:** a fixture for an ADB parser must
reproduce the real *shape* of the output, index prefixes and all. Green unit
tests are not evidence about a device. This vindicates the Chief Engineer's
standing position and it is recorded here so it is not relearned expensively.

### The acceptance run (CE, 14-Oct) — required before the build

Four stages, executed in order, ending in a written report:

1. **Remotely restart** the demo device.
2. **Scan** and gather every hardware parameter the product is meant to collect.
3. **Purge**, and finish with a factory restart — remotely.
4. **Write the actual report** and verify, against what was set out to be built,
   whether it is genuinely done — in rows and columns, and in plain English.

**What "remotely" has to mean, stated before we start.** Every device in this programme
is attached by USB to a single workstation. So *remotely* here means **driven end to end
from the workstation, with the operator never touching the handset** — not reached over a
network from another location. That is achievable and is worth proving. Claiming network
distance we do not have would be the first overstatement of the run.
