CYVRA CUSTOMER WORKSPACE

World-Class Customer Dashboard — Product, UX, Reporting & Engineering Architecture

CYVORIQ Solutions Pvt. Ltd. | CYVRA Mobile

Version 1.0 — Customer Workspace Redesign Specification

------------------------------------------------------------------------

1. PURPOSE

This specification defines the redesigned customer-facing Workspace at:

https://cyvoriq.co.in/dashboard

The Workspace is the customer’s operational control centre for CYVRA
Mobile.

It is not intended to be a payment gateway, an online banking screen, or
merely an application-download page.

The Workspace shall provide one clean, professional environment for:

1.  CYVRA Mobile licence selection/request.
2.  Manual payment-status recording.
3.  Licence authorization/status visibility.
4.  CYVRA Mobile application download.
5.  Existing Update and Upgrade functions.
6.  Raw diagnostic/purge report upload.
7.  Evidence organization and audit-report generation.
8.  Device-level scan/report tracking.
9.  Own-device and third-party-device audit operations.
10. Settings.
11. Help and support.

The design must communicate that CYVRA Mobile is an evidence-led
diagnostic, sanitization and reporting platform.

Core product message:

“Know the Device. Prove the Result.”

Broader positioning:

“From Device Intake to Final Disposition—Built on Evidence.”

------------------------------------------------------------------------

2. IMPORTANT COMMERCIAL RULE — NO PAYMENT GATEWAY

The Customer Workspace SHALL NOT integrate a payment gateway.

There shall be no card, UPI, bank-transfer, payment-processor or
checkout integration inside this dashboard.

The purchase area only records the commercial/licensing state.

The customer selects the desired CYVRA Mobile Licence Type and the
dashboard captures the required customer information.

A simple Payment Status control shall be provided.

Recommended states:

-   Not Done
-   Done

The exact internal enum may be:

PAYMENT_NOT_CONFIRMED PAYMENT_CONFIRMED

The dashboard is not responsible for processing the payment.

3. LICENCE AUTHORIZATION PRINCIPLE

The licence received by the customer at the registered email address is
the operational authorization signal.

Customer-facing logic:

1.  Customer selects a licence model.
2.  Customer provides/validates required customer information.
3.  Payment status is recorded manually by the authorized business/admin
    process.
4.  Licence is issued through the existing licensing/approval process.
5.  Licence is delivered to the customer’s registered email address.
6.  Receipt of a valid issued licence means the customer is authorized
    to use the corresponding licensed CYVRA Mobile entitlement, subject
    to the existing licensing rules.
7.  The Workspace displays the resulting licence/application status.

The Customer Workspace therefore should not duplicate the administrative
approval engine.

It should display the customer’s authoritative entitlement state.

Recommended customer-facing status model:

-   Request Not Submitted
-   Request Submitted
-   Payment Not Confirmed
-   Awaiting Authorization
-   Licence Issued
-   Ready to Download
-   Active
-   Expired
-   Suspended
-   Upgrade Available

Do not expose internal administrative workflow details unnecessarily.

4. DESIGN PHILOSOPHY

The current dark-blue dashboard shall be replaced.

The new design should feel like a professional enterprise audit and
evidence platform.

Visual direction:

-   Light professional steel background.
-   White or very-light steel cards.
-   Subtle grey borders.
-   High readability.
-   Strong hierarchy.
-   Generous whitespace.
-   Minimal gradients.
-   No oversized decorative graphics.
-   No dark navy page-wide background.
-   No excessive neon colours.
-   No gaming-style dashboard appearance.

Colour semantics must be consistent:

GREEN Meaning: - Completed - Successful - Approved - Active - Ready -
Verified

RED Meaning: - Error - Failed - Rejected - Blocked - Attention
required - Missing required action

ORANGE Meaning: - Download - Application package - Export/download
action - Important customer action related to obtaining a file

STEEL/GREY Meaning: - Neutral - Informational - Secondary - Disabled -
Pending/non-action state

The UI must never use colour alone to communicate a critical state.
Every status should also contain text or an icon/semantic label.

16. REPORTING & AUDIT — CORE PURPOSE

Reporting & Audit is a major part of the new Workspace.

It should not be treated as a simple “upload file” screen.

It is an evidence processing and audit-report workspace.

The conceptual flow is:

CYVRA MOBILE Device Connection → Identity → Android/Software → Hardware
→ Storage → Memory → Battery → Security → Network → Applications →
Capability → Diagnostic Result → Sanitization/Purge → Post-Purge
Verification → Raw Report

THEN

CUSTOMER WORKSPACE Raw Report Upload → Validate → Extract Evidence →
Normalize → Map Evidence Domains → Add Customer/Audit Metadata → Build
Audit Record → Generate Professional Report → Authorize/Approve → Audit
Seal → Final Report

17. RAW REPORT UPLOAD

Customer can upload the raw report produced by CYVRA Mobile after
scanning and/or purging.

The upload screen should show:

-   File selector
-   Accepted file type(s)
-   Maximum file size
-   Upload progress
-   Validation status
-   Processing status
-   Error details if validation fails

The system must not silently accept malformed or unrelated files.

------------------------------------------------------------------------

18. REPORT INGESTION PIPELINE

Recommended engineering pipeline:

1.  Receive upload.
2.  Generate upload/request ID.
3.  Validate file type.
4.  Validate file integrity.
5.  Parse report.
6.  Validate schema/version.
7.  Identify device/session.
8.  Extract evidence records.
9.  Preserve source provenance.
10. Normalize data into the reporting model.
11. Separate automated evidence from physical verification.
12. Preserve unknown/restricted/conditional states.
13. Attach customer/audit metadata.
14. Generate report-ready dataset.
15. Generate final report.
16. Store report version and audit history.

Raw evidence should never be silently overwritten by transformed data.

------------------------------------------------------------------------

19. EVIDENCE-FIRST REPORTING PRINCIPLE

The dashboard and generated reports must follow:

EVIDENCE BEFORE GRADING.

Missing or restricted data must NOT automatically become PASS or FAIL.

The system must preserve the distinction:

ENUMERATED ≠ PHYSICALLY PRESENT ≠ FUNCTIONALLY TESTED

This is a core engineering and audit principle.

22. CAPABILITY SEMANTICS

The system must preserve capability states such as:

YES PARTIAL CONDITIONAL ASSISTED NO

These must not be flattened into a simplistic PASS/FAIL value.

Example:

Battery swelling: CYVRA software capability = NO Physical verification =
YES

Therefore the report should communicate:

“Physical verification required”

rather than:

“Battery swelling = PASS”

------------------------------------------------------------------------

23. RESULT SEMANTICS

Recommended result vocabulary:

PASS FAIL NOT TESTED NOT AVAILABLE NOT APPLICABLE CONDITIONAL ASSISTED
PHYSICAL VERIFICATION REQUIRED RESTRICTED UNKNOWN ERROR

A missing permission, unavailable OEM source or restricted identifier
must not automatically become FAIL.

------------------------------------------------------------------------

24. IDENTIFIER RULE

Never fabricate:

-   IMEI
-   Serial
-   MAC
-   Other restricted identifiers

If unavailable:

Record source/status.

Examples:

NOT EXPOSED RESTRICTED NOT AVAILABLE NOT COLLECTED CONDITIONAL

The report must make the provenance clear.

------------------------------------------------------------------------

25. PHYSICAL VERIFICATION

CYVRA Mobile can guide physical verification, but the system must never
falsely claim that a software test has verified a physical condition.

The application/workspace should distinguish:

SOFTWARE EVIDENCE FUNCTIONAL SOFTWARE TEST ASSISTED PHYSICAL
VERIFICATION PHYSICAL VERIFICATION SPECIALIZED SERVICE VERIFICATION

Examples requiring physical/assisted verification include:

-   Glass cracks/chips
-   Dead/stuck pixels
-   Burn-in
-   Lens glass condition
-   Speaker distortion
-   Microphone acoustic quality
-   Button tactile quality
-   USB connector condition
-   Charging connector looseness
-   SIM tray/slot integrity
-   Battery swelling
-   Liquid/corrosion evidence
-   Chassis deformation
-   Water-resistance/IP seal
-   Internal service-level conditions

------------------------------------------------------------------------

26. PHYSICAL VERIFICATION REPORTING

The report should provide structured fields for physical checks.

Example:

CHECK: Battery swelling

RESULT: CLEAR / SUSPECTED / REMOVE

EVIDENCE: Observation + optional photograph

OPERATOR: Named operator if applicable

TIMESTAMP: Recorded timestamp

This prevents human observations from being silently presented as
automated software evidence.

------------------------------------------------------------------------

27. HYBRID TEST MODEL

Some tests are best represented as:

CYVRA TEST STIMULUS + TECHNICIAN CONFIRMATION

Examples:

-   Display patterns
-   Touch grid
-   Camera quality
-   Audio
-   Buttons
-   Charging
-   Wi-Fi controlled test
-   Bluetooth controlled test
-   Cellular controlled test
-   GNSS test

The reporting model should preserve both parts.

Example:

Software test: COMPLETED

Technician confirmation: PASS

Final evidence: HYBRID VERIFIED

------------------------------------------------------------------------

28. SANITIZATION / PURGE REPORTING

The purge lifecycle must be represented as:

Capability → Authorization → Method → Purge/Reset → Reboot → Reconnect →
Post-Purge Verification → Final Report

The reporting system should capture:

-   Purge capability assessment
-   Purge authorization
-   Supported method
-   Execution start
-   Execution result
-   Reboot completion
-   Reconnection
-   Post-purge state
-   Residual-data evidence where supported
-   Exceptions
-   Final disposition

------------------------------------------------------------------------

29. PURGE RESULT PRINCIPLE

The system must not claim more than the available evidence proves.

For example:

Physical NAND cell-level verification is not available through normal
Android/Windows software.

Therefore the report must not claim:

“NAND cells physically verified clean.”

Instead it may report the actual supported post-purge evidence and
clearly state limitations.

38. AUDIT SEAL

A formal CYVRA Audit Seal is required.

The seal should eventually communicate:

-   Authentic CYVRA report
-   Report identity
-   Report/reference number
-   Verification mechanism if implemented
-   CYVORIQ technology provenance

The seal design is NOT to be improvised as a decorative graphic.

It should be designed as a controlled report-authenticity mark.

39. REPORT INTEGRITY

SHA-256 Report Version Generated Timestamp

40. REPORT VERSIONING

A report should not simply be overwritten.

Recommended model:

Each version should preserve:

-   Who generated it
-   When
-   Why it changed
-   Source data
-   Report template/version
-   Evidence version
-   Customer metadata version

Finalized reports should be immutable unless a controlled correction
workflow exists.

49. AUDIT BATCH

For customers processing multiple devices, introduce an AUDIT BATCH
concept.

Example:

AUDIT BATCH: ABC-ITAD-2026-001

Contains:

Device 001 Device 002 Device 003 … Device N

This allows multiple device reports to be grouped under one audit event.

The individual device reports remain independently traceable.

------------------------------------------------------------------------

50. ONE DEVICE = ONE TRACEABLE RECORD

The system must maintain device-level traceability.

Even if several devices are processed under one audit batch:

One device

One device/session record.

One report

One traceable report record.

This prevents mixed-device evidence and improves audit defensibility.

------------------------------------------------------------------------

51. REPORT UPLOAD SAFETY

The upload processor should reject or quarantine:

-   Unsupported file type
-   Corrupt file
-   Unknown report version
-   Missing required device/session identity
-   Invalid schema
-   Duplicate upload where appropriate
-   Tampered/inconsistent package where detectable

The UI should explain the problem in plain language.

Never display a generic:

“Something went wrong.”

Instead:

“Report could not be processed because the report schema version is
unsupported.”

------------------------------------------------------------------------

52. DUPLICATE REPORT HANDLING

If the same raw report is uploaded twice:

Do not silently create two identical audit records.

The system should detect duplicates using appropriate report/session
identifiers and/or cryptographic hashes.

UI:

“Duplicate report detected.”

Then provide:

-   View existing record
-   Replace/re-upload if permitted
-   Cancel

59. COVERAGE DASHBOARD

The engineering coverage dashboard can inform the reporting
architecture.

It should communicate:

CYVRA can collect extensive software/system evidence and actively
exercise many device functions.

However:

Physical verification remains essential for conditions software cannot
directly observe.

The customer-facing UI should NOT advertise unsupported claims such as:

“100% device health verified.”

Instead use evidence-based wording.

60. GRADING POLICY

Overall grading must remain a separate policy layer.

Evidence collection ≠ grading

Diagnostic result ≠ commercial grade

Missing/restricted evidence ≠ automatic FAIL

The Workspace report engine should therefore preserve evidence first and
apply grading rules separately if/when a grading policy is configured.

A refurbishment company owns a CYVRA Mobile licence.

It receives 50 phones from Customer X.

The company scans the phones.

-   Device identity
-   Evidence
-   Diagnostic result
-   Physical verification
-   Purge result
-   Report result

75. RAW DATA VS NORMALIZED DATA

Keep these separate.

NORMALIZED EVIDENCE Structured representation extracted from the raw
report.

FINAL REPORT Human-readable audit artifact generated from normalized
evidence + audit metadata.

Never destroy the raw evidence when generating the final report.

------------------------------------------------------------------------

76. SOURCE-OF-TRUTH MODEL

For diagnostic evidence:

CYVRA Mobile raw result is the original operational source.

For customer identity:

Authenticated customer/account is authoritative.

For licence:

Existing licensing/authorization service is authoritative.

For report metadata:

Customer-entered audit metadata is authoritative after validation.

For final report:

Report generation service creates the controlled artifact.

For authorization:

The licensed purchasing company is the report authorizing entity.

For technology provenance:

CYVORIQ SOLUTIONS PVT. LTD.

------------------------------------------------------------------------

77. REPORT FINALIZATION

Before finalizing:

System validates:

-   Customer information complete.
-   Device/session identified.
-   Required evidence present or explicitly marked unavailable.
-   Physical verification requirements addressed or marked not
    performed.
-   Sanitization status known.
-   Exceptions acknowledged.
-   Report metadata complete.

Then:

GENERATE FINAL REPORT

After finalization:

REPORT FINALIZED Green.

The report should become controlled/immutable unless a formal
correction/revision mechanism exists.

------------------------------------------------------------------------

78. REPORT QUALITY GATE

The system should never generate a polished-looking report that hides
incomplete evidence.

If required information is missing:

RED / WARNING:

“Report cannot be finalized. Physical verification is incomplete.”

or:

“Report contains unresolved critical exceptions.”

The report may still be saved as a draft if policy allows.

------------------------------------------------------------------------

79. DRAFT VS FINAL REPORT

Recommended states:

DRAFT Evidence/data still being prepared.

READY FOR REVIEW All required data collected.

FINALIZED Report approved/locked.

REVISED A controlled revision exists.

VOID Report invalidated with reason.

This is preferable to silently replacing an old report.

81. DEVICE SCAN WORKFLOW

The Workspace does not replace the Windows application.

------------------------------------------------------------------------

82. NO FALSE AUTOMATION

The reporting engine must never convert:

“not observable”

into:

“pass”

and must never convert:

“not tested”

into:

“fail”

Examples:

Battery swelling: Software cannot determine it. Result: PHYSICAL
VERIFICATION REQUIRED.

USB connector looseness: Software cannot determine it reliably. Result:
PHYSICAL VERIFICATION REQUIRED.

NAND cell-level verification: Not reliably determinable through normal
workflow. Result: NOT AVAILABLE / OUTSIDE NORMAL SOFTWARE VERIFICATION.

------------------------------------------------------------------------

83. REPORT LANGUAGE

Use professional evidence language.

Avoid:

“Device is perfect.”

Prefer:

“CYVRA evidence indicates the tested functions listed below completed
successfully. Physical condition items requiring technician inspection
are reported separately.”

Avoid:

“100% clean.”

Prefer:

“Post-purge verification completed for the supported evidence paths
listed in this report.”

This is critical for audit defensibility.

85. PHYSICAL VERIFICATION MATRIX INTEGRATION

PV-005 Touch edge/corner condition

PV-011 USB port condition/retention

PV-015 Battery swelling

PV-016 Liquid/corrosion evidence

The report should identify whether each required check was:

COMPLETED NOT COMPLETED NOT APPLICABLE REQUIRES SERVICE

For example:

High confidence controlled fixture test

Conditional OEM source
