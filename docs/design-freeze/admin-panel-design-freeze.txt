============================================================ 1. PURPOSE
OF THIS DOCUMENT
============================================================
This document is the consolidated design freeze for the CYVRA Mobile
Admin Panel.
It combines the existing CYVRA Mobile Admin Licence Approval & Control
Center design plan with the latest approved operational requirements.
The purpose is to define one clear, professional, implementation-ready
admin experience for:
-   customer licence requests
-   customer identity visibility
-   payment confirmation
-   licence-plan selection
-   licence issuance
-   host/workstation binding visibility
-   activation visibility
-   licence revocation
-   staff and role control
-   audit history
-   reporting
-   operational search and filtering
This is a product and UX/system design specification. It is not a
replacement for the existing CYVORIQ licence engine or cryptographic
licence-generation service.
The central design principle is:
ONE ROW = ONE CUSTOMER LICENCE REQUEST
This principle is mandatory and must remain visible in the design,
database interpretation, workflow and administrator experience.
============================================================ 2. CORE
PRODUCT POSITION
============================================================
CYVRA Mobile is the mobile-device verification, sanitization and
evidence platform.
The Admin Panel is the operational control center for customer licence
requests.
The Admin Panel is NOT the customer application.
The Admin Panel is NOT the CYVRA Mobile desktop application.
The Admin Panel is NOT the cryptographic licence-generation engine.
The Admin Panel is the controlled administrative layer that allows
authorized CYVORIQ staff to review customer licence requests, verify
payment, authorize issuance, issue licences through the existing licence
engine, monitor activation/binding, and revoke licences when required.

============================================================ 3. MOST
IMPORTANT BUSINESS RULE
============================================================
ONE ROW = ONE CUSTOMER LICENCE REQUEST.
This means:
-   Every customer licence request is represented by one row in the
Licence Registry.
-   The row has a sequential display number: 1, 2, 3, 4, 5…
-   The sequential number is NOT the licence ID.
-   The licence ID is a separate immutable system identifier.
-   The customer email identifies the customer account.
-   A customer may have more than one historical licence record when the
business legitimately requires it.
-   A row represents the licence request/record, not an individual
mobile phone.
-   A row does not represent a USB port.
-   A row does not represent the customer’s Windows laptop.
-   A row does not represent an individual employee using the software.
The table is therefore a licence-operations register.
The administrator must be able to understand the complete licence
pipeline by looking at the rows without opening every record.
============================================================ 4. LATEST
APPROVED LICENCE SEMANTICS
============================================================
The licence model must remove ambiguity between:
A. Customer B. Host workstation C. Mobile-device capacity
4.1 CUSTOMER / LICENCE HOLDER
The customer is primarily identified by the verified registered email
address.
User ID = registered email ID.
The same verified customer identity used by the customer-facing CYVORIQ
account should be reflected in the Admin Panel.
The Admin Panel must not duplicate or expose the customer’s password.
The Admin Panel reads customer identity and licence-request information
from the authoritative customer/licence systems.
Required identity fields include:
-   Registered Email
-   User ID
-   PIN Code / Postal Code
-   Customer Name where available
-   Company where available
-   Customer Type where available
4.2 HOST WORKSTATION
A desktop licence is activated on one Windows laptop or desktop.
The host workstation is the computer on which the CYVRA Mobile desktop
application is installed.
The host is NOT the mobile phone/tablet.
Current commercial rule:
Host Workstation Limit = 1
for all standard plans.
4.3 MOBILE DEVICE CAPACITY
The commercial licence determines the number of mobile devices the
customer is entitled to process.
The current plans are:
CYVRA Mobile — 1 Mobile Device
CYVRA Mobile — 5 Mobile Devices
CYVRA Mobile — 10 Mobile Devices
CYVRA Mobile — 25 Mobile Devices
CYVRA Mobile — 50 Mobile Devices
Internal plan codes may be:
PLAN-1
PLAN-5
PLAN-10
PLAN-25
PLAN-50
or equivalent CAP-1 / CAP-5 / CAP-10 / CAP-25 / CAP-50 identifiers.
Do not describe these plans as “1 user 1 device” in customer-facing
language.
Recommended explanation:
"One workstation licence. Mobile-device processing capacity:
1 / 5 / 10 / 25 / 50 devices."
4.4 USB / DEVICE CAPABILITY
The CYVRA Mobile application is designed to support up to 50 mobile
devices through one USB setup/connection environment, subject to the
actual application implementation and supported hardware configuration.
This capability must not be confused with the commercial licence plan.
The licence capacity is an entitlement.
The physical USB/device handling capability is an application/system
capability.
The Admin Panel must keep these concepts separate.
============================================================ 5. CUSTOMER
JOURNEY ============================================================
The intended end-to-end journey is:
1.  Customer visits:
https://cyvoriq.co.in/
2.  Customer creates an account.
3.  Email OTP verification is completed.
4.  Customer selects/purchases a CYVRA Mobile licence model.
5.  The customer’s verified identity and licence request become
available to the Admin Panel.
6.  The Admin Panel creates/displays one customer licence-request row.
7.  The row initially shows payment as PENDING unless payment has
already been confirmed by an authoritative payment process.
8.  Admin reviews the customer record.
9.  Admin confirms payment.
10. The row becomes eligible for issuance.
11. The system changes the operational state to:
READY TO ISSUE
12. Admin presses the green:
ISSUE LICENCE
13. The existing authoritative licence engine/API provisions the licence
credential and signed serial/digest as part of the issue operation.
14. Admin does NOT manually create cryptographic licence material.
15. The licence is issued.
16. Customer receives the licence information through the configured
customer communication channel.
17. Customer downloads and launches CYVRA Mobile.
18. Customer activates the licence on one Windows laptop/desktop.
19. Host binding is recorded.
20. Licence becomes ACTIVE after successful activation.
21. Admin can view activation, host binding, audit history, resend,
suspend where permitted, or revoke where authorized.
============================================================ 6. ADMIN’S
PRIMARY RESPONSIBILITY
============================================================
The Admin’s responsibility is:
VERIFY -> AUTHORIZE -> ISSUE -> CONTROL -> AUDIT
The Admin is NOT expected to manually generate a cryptographic licence
key.
The authoritative licence engine remains responsible for:
-   licence serial creation
-   cryptographic signing
-   signed digest/credential creation
-   licence validity
-   backend entitlement enforcement
The Admin Panel is responsible for:
-   displaying requests
-   validating administrative prerequisites
-   recording payment confirmation
-   confirming the selected licence plan
-   initiating the issue operation
-   showing the result
-   recording who issued the licence
-   recording when it was issued
-   allowing authorized revocation
-   maintaining an auditable operational history
============================================================ 7.
IMPORTANT CONFLICT RESOLUTION
============================================================
The earlier design contained concepts such as:
+ New Licence
Generate Licence Key
Ready to Generate
Approve & Issue
The latest approved operational requirement changes these semantics.
7.1 REMOVE “+ NEW LICENCE” FROM THE PRODUCTION PRIMARY WORKFLOW
Customer registration/purchase creates the customer licence request.
The Admin should not manually retype a customer and create a completely
new licence request merely to issue the purchased licence.
Therefore the production Admin Panel should be request-first.
The main Licence Registry should not require a “+ New Licence” button
for ordinary customer purchases.
A controlled manual creation/import mechanism may exist later for
authorized exceptional cases, but it is not the normal customer journey.
7.2 “GENERATE” IS NOT THE ADMIN’S PRIMARY ACTION
The Admin should not manually generate the licence.
The system/licence engine generates the signed credential.
The Admin’s visible primary action is:
ISSUE LICENCE
7.3 RENAME “READY TO GENERATE”
The administrative status should be:
READY TO ISSUE
not:
READY TO GENERATE
7.4 FINAL ACTION MODEL
Before payment:
ISSUE LICENCE
Disabled / Grey
After payment is valid and all prerequisites are satisfied:
ISSUE LICENCE
Green / Enabled
After successful issue:
ISSUED
After customer activation:
ACTIVE

============================================================ 20. ISSUE
LICENCE BUTTON
============================================================
This is one of the most important frozen UI rules.
The final row action is:
ISSUE LICENCE
Visual treatment:
GREEN
The button is enabled ONLY when:
-   customer identity is valid
-   email is verified/eligible
-   payment is PAID
-   licence plan is valid
-   request is eligible for issuance
-   no conflicting issued licence exists
-   the administrator has permission
-   the backend licence engine is available
Before these conditions are satisfied:
ISSUE LICENCE
Disabled / Grey
The frontend button state is only a usability feature.
The backend MUST independently validate all conditions.
The browser cannot be trusted to authorize issuance.
============================================================ 21. ISSUE
LICENCE — WHAT ACTUALLY HAPPENS
============================================================
When the Admin presses:
ISSUE LICENCE
the Admin Panel requests the authoritative licence service to provision
the licence.
The licence service generates the required signed licence serial/digest
or credential.
The Admin Panel does not implement cryptographic signing in JavaScript
or browser code.
The operation should be treated as one controlled business transaction.
Conceptually:
Admin clicks Issue
|
v
Backend validates request
|
v
Payment = PAID?
|
v
Plan valid?
|
v
Customer eligible?
|
v
Existing conflicting licence?
|
v
Call authoritative licence engine
|
v
Signed licence credential created
|
v
Licence state = ISSUED
|
v
Audit event created
|
v
Customer communication queued

============================================================ 25. RED
REVOKE BUTTON
============================================================
At the far right of each row there must be a prominent red:
REVOKE
button/action.
The user explicitly requires:
One green Issue button
One red Revoke button
at the end of each row.
The system may disable the Revoke action for states where revocation is
not valid, but the operational design must make the control obvious.
Revoke means:
Permanent administrative invalidation of the licence credential.
Revoke is NOT:
Delete record
Revoke is NOT:
Suspend
Revoke is NOT:
Remove audit history
The licence record must remain in the system.

============================================================ 27. SUSPEND
VS REVOKE ============================================================
SUSPEND:
Temporary administrative stop.
REVOKE:
Permanent invalidation.
These are separate actions.
Suspended licences may later return to ACTIVE if policy permits.
Revoked licences should not simply become active again.
Both actions require auditability.

============================================================ 41. ERROR
HANDLING ============================================================
Errors must be written in operational language.
Bad:
HTTP 409
Better:
This licence was already processed by another administrator.
Refresh the record to see the current state.
Bad:
INVALID_STATE
Better:
This licence has already been issued and cannot be issued again.
Bad:
PAYMENT_FALSE
Better:
Licence cannot be issued because payment has not been confirmed.
Technical details may be available through:
View technical details
but should never be the primary message for ordinary staff.
============================================================ 42.
CONCURRENCY PROTECTION
============================================================
Two administrators must never be able to issue the same licence
simultaneously.
Example:
Admin A clicks Issue
Admin B clicks Issue
Only one operation may succeed.
The second receives:
This licence was already processed by another administrator.
Refresh the record to view the latest status.
This must be enforced by the backend using an atomic state transition or
equivalent transaction control.
Frontend button disabling alone is insufficient.
============================================================ 43.
IDEMPOTENCY ============================================================
Issue operations should be idempotent where practical.
If the browser loses connection after the server completes issuance, a
retry must not create a second valid licence.
The backend should recognize the request/result and return the existing
operation result where appropriate.
This is especially important for licence issuance because it is a
high-impact operation.

CYVORIQ'S CONTROL CENTER FOR CYVRA MOBILE LICENCE OPERATIONS
