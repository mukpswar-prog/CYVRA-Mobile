1. ARCHITECTURAL FOUNDATION & VERSION 2.1.1 UPGRADE PURPOSE
================================================================================
In Version 2.0.1, sanitization eligibility was gated strictly on an enterprise 
Device Owner privilege check (`deviceOwnerActive == true`). While appropriate for 
enterprise MDM environments, this caused standard unprovisioned consumer 
devices (e.g., Samsung Galaxy A10s) to be artificially blocked from sanitization 
with "DEVICE_OWNER_NOT_PROVISIONED", even when the device possessed hardware-backed 
File-Based Encryption (FBE) capable of instantaneous cryptographic data erasure.

Version 2.1.1 upgrades the system to Option C (Hybrid Capability-Based Architecture):
• Device connection != Device Owner provisioning != Sanitization capability.
• The engine evaluates the real hardware, encryption state, and firmware capabilities 
  of each phone dynamically.
• If Device Owner is present, it executes Tier 1 Device Owner wipe.
• If Device Owner is absent, but hardware File-Based Encryption (FBE) is active, it 
  qualifies and executes Tier 2 Cryptographic Erase (key eviction).
• If an OEM wipe utility is available, it qualifies Tier 3 OEM Secure Erase.
• If unencrypted legacy storage is present, it qualifies Tier 4 Platform Reset.
• Only untrusted, rooted, or unsupported environments trigger Tier 5 Blocker.
• 100% of Version 2.0.1 features, UI layouts, report generators, and security 
  safeguards are preserved without regression.

5. OPTION C: DYNAMIC HYBRID SANITIZATION QUALIFICATION ENGINE
================================================================================
HostSanitizationQualificationEngine evaluates on-device telemetry and ADB 
evidence to select the optimal, cryptographically sound sanitization tier:

• TIER 1: CLEAR_DEVICE_OWNER_WIPE
  - Conditions: Device Owner active (`deviceOwnerActive == true`) AND wipe allowed.
  - Action    : Dispatches authorized enterprise wipe via `DevicePolicyManager.wipeData()`.
  - Standard  : Complies with NIST SP 800-88 R1 "Clear" standard for managed fleets.

• TIER 2: PURGE_CRYPTOGRAPHIC_ERASE
  - Conditions: File-Based Encryption (FBE) active (`storageEncryptionStatus == 5` or 
    `isEncrypted == true`) AND hardware-backed KeyStore/TEE present.
  - Action    : Destroys master volume encryption keys (KEK/DEK), evicts Keystore 
    credentials, and executes platform recovery erase.
  - Standard  : Complies with NIST SP 800-88 R1 "Purge" standard (Cryptographic Erase).
  - Outcome   : Target data rendered mathematically unrecoverable.

• TIER 3: PURGE_OEM_SECURE_ERASE
  - Conditions: Supported Samsung / Google OEM secure recovery erase service available.
  - Action    : Triggers authenticated OEM hardware secure erase command block.
  - Standard  : Complies with NIST SP 800-88 R1 "Purge" standard.

• TIER 4: CLEAR_PLATFORM_RESET
  - Conditions: Legacy Android device without full FBE, or unencrypted storage.
  - Action    : Dispatches authorized platform factory reset (`recovery --wipe_data` 
    or `masterClear`).
  - Standard  : Complies with NIST SP 800-88 R1 "Clear" standard.

• TIER 5: TECHNICAL_BLOCKER
  - Conditions: Rooted kernel detected, custom ROM / modified bootloader, tampered 
    su binaries, or unresolvable security conflict.
  - Action    : Execution refused; outputs explicit technical explanation.
  - Standard  : Prevents issuing unverified or compromised certificates.

6. MULTI-SIGNAL POST-RESET VERIFICATION & INTEGRITY PROOF
================================================================================
CYVRA Mobile never treats an accepted wipe command as proof of erasure. 
HostSanitizationProvider enforces independent post-reset verification across 
multiple orthogonal signals:

1. Provisioning State Check:
   • Queries `settings get global device_provisioned`.
   • Must return `0` (indicating the device is in pristine OOBE out-of-box setup state).
2. Zero Account Invariant:
   • Verifies that zero user, Google, Samsung, or enterprise accounts exist.
3. Zero Third-Party Application Invariant:
   • Verifies that 0 third-party packages remain installed on `/data/app`.
4. Screen Lock & Credential Eviction:
   • Verifies that all PINs, passwords, patterns, and biometric credentials are gone.
5. Invariant Reporting:
   • Discloses all measured verification counts honestly in the certificate limitations.

7. REPORTING, CERTIFICATION & TAMPER-EVIDENT SEALS (PDFBOX 3.0.3)
================================================================================
The reporting subsystem generates official, cryptographically verifiable certificates:

A. Dual Document Architecture:
   • Verified Success: Generates official "CYVRA Data Sanitization & Verification Certificate" 
     with certificate identifier `CYVRA-CERT-<UUID>-<TIMESTAMP>`.
   • Blocked / Refused: Generates "CYVRA Data Sanitization Assessment Report" with 
     identifier `CYVRA-ATTEMPT-<UUID>-<TIMESTAMP>`.

B. Tamper-Evident Report Artifacts:
   • Vector PDF Certificate: Produced using Apache PDFBox 3.0.3 with embedded 
     high-resolution CYVORIQ branding, security hashes, and operator stamps.
   • Machine-Readable Audit JSON (`report.json`): Complete structured dump of all 
     48 parameters, agent telemetry, execution timings, and post-reset verification.
   • Cryptographic Trust Manifest (`manifest.json`): SHA-256 hashes of all generated 
     report components for independent integrity verification.

C. Zero Serial Leakage Guarantee:
   • Raw hardware serial numbers and IMEI numbers are strictly excluded from 
     operator reports and export titles.
   • Reports use the opaque reference `DEV-XXXXXXXX` derived from session UUID.

================================================================================

   • Stored at `<cyvra.home>/ledger.jsonl`.
   • Records every workstation lifecycle event: ACTIVATION, HW_SCAN, APP_SCAN, 
     SANITIZE_START, SANITIZE_VERIFY, DEACTIVATION.
